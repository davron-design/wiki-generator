Beginner's Guide
Latest release v2026-10-02 What's new→

Building the Agentic Mind.

A friendly walkthrough for setting up an AI-powered knowledge base with Claude Code, and for collaborating on it with your team. No terminal. No coding.

New to Git, GitHub, repositories, commits, or push / pull?
Git & GitHub
Git is the free tool that does the actual change-tracking, running quietly on your own computer — Claude Code uses it behind the scenes, which is why you install it once during setup. GitHub is the website built on top of it, where teams keep their folders in sync with a complete history of every change (owned by Microsoft, used by millions). In short: Git is the engine, GitHub is the cloud home where the team shares the work.
Repository (or "repo")
The shared folder on GitHub itself — your wiki, but in the cloud. Like a Google Drive folder, except every edit is tracked and you can roll back to any earlier version.
Commit
A saved snapshot of your changes — one recorded step in the wiki's history. When you click Commit to main in GitHub Desktop, you're stamping your edits with a short message so everyone can see what changed and when.
Push and Pull
Pull = grab the latest changes from GitHub onto your computer. Push = send your own changes back up so the rest of the team can see them. You'll do both with one-click buttons in GitHub Desktop.

01
Get Started

Set it up in 10 minutes.

In about ten minutes you'll have an AI-powered wiki running on your computer — even if you've never installed a developer tool before.

0

Install Claude Code

If you don't already have it, download the Claude Code desktop app from claude.com/claude-code. It's free, installs in under a minute, and works on Mac and Windows.

Sign in once you've launched it — that's the only account you need for this whole section.

1

Install Git

Git is a small, free tool Claude Code needs to download skills. The first time you open Claude Code it usually says Git is missing — so let's install it now.

Windows — go to git-scm.com/install/windows, click Download, then run the file and click through the installer. The defaults are fine.

Mac — open the Terminal app (press Cmd + Space, type Terminal, hit Enter), then paste this line and press Enter:

xcode-select --install

A window pops up — click Install and let it finish. Then reopen Claude Code and the "Git is missing" warning will be gone.

2

Create a folder for your wiki

Pick a spot on your computer — your Desktop is fine. Create a new folder and name it whatever you want: My Wiki, Gardening Notes, Work Knowledge Base.

That folder is the home of your wiki. Everything will live inside it.

3

Open the folder in Claude Code

Launch the Claude Code desktop app and open the folder you just created. You should now see an empty project with a chat box ready to go.

4

Install the wiki generator skill

Paste this prompt into Claude Code:

Please download the repo at https://github.com/davron-design/wiki-generator and install it as a project-scoped skill in this folder. Put the skill files under .claude/skills/wiki-generator/ so the skill only applies to this project. Once it's installed, list the skills so I can confirm it's ready to use.

Don't worry about the technical words inside — just paste the whole block as-is. Claude handles the rest.

If Claude asks for permission, just Always Allow. You only need to do this once per wiki.

5

Build your wiki project

In Claude Code, type:

/wiki-generator

If Claude doesn't recognize it, start a new session in the same folder and type it again. A skills folder created during a session loads in the next one.

Claude will create three folders for you:

  • raw/ — where you drop source files (articles, notes, research)
  • wiki/ — where the polished knowledge base lives
  • output/ — where reports and query results show up

It also installs three companion skills inside your wiki folder: /raw-compile, /audit-wiki and /update-wiki. Each wiki keeps its own copies, so updating one wiki leaves the others as they are.

When it's done, start a new session in the same folder before your first compile. Claude Code reads the wiki's CLAUDE.md only when a session starts.

What's a skill?

A skill is a small package of instructions that teaches Claude how to do a specific job. You install it once, then trigger it by name with a slash command — like /wiki-generator above.

Think of it as a shortcut for a complex task: instead of writing out detailed instructions every time, you say the skill name and Claude follows the recipe.

6

Add files to raw/

This is where you feed your wiki. Open the raw/ folder and drop in any files you want included: articles, notes, research clippings, transcripts, PDFs, images, PowerPoint decks, Word documents and Excel spreadsheets.

Optional: install the free LibreOffice. When it's installed, Claude renders each slide and page of a deck or document and reads the pictures and charts on it. Claude reports anything in a file it couldn't open.

Add as many files as you want. Don't worry about organizing them — that's Claude's job.

7

Compile the raw files

In Claude Code, simply say:

compile

Claude will read every file in raw/, group the files by topic, write clean wiki articles into wiki/, link them together with [[wiki links]], and archive the compiled raw files so you know what's been processed.

Sit back — this part is automatic.

8

Audit your wiki

Once your wiki is built, check it for gaps or inconsistencies. In Claude Code, say:

audit

Claude will scan the wiki and produce a numbered audit report in output/_audits/. The report points out missing cross-links, thin topics, and inconsistencies between articles.

The audit is report-only by default — it won't change anything until you say so.

9

Keep your wiki up to date

The compile and audit rules improve over time. Your wiki carries its own copy of them, so it runs whatever version it was built with until you refresh it. In Claude Code, say:

update

Claude checks the version your wiki is on against the latest published one, shows you what changed since then, and asks before writing anything. It only ever rewrites four files: CLAUDE.md and the three skills. Your articles, your raw sources and your audit reports are never touched.

The new compile and audit rules apply right away. If the update rewrote CLAUDE.md, start a new session in the folder, because Claude Code reads that file only when a session starts. update tells you when this applies.

Nothing happens when I say update

Wikis built before this feature existed have no /update-wiki skill to run. Paste this into Claude Code once, from inside your wiki folder:

Run this exact command with Bash in this folder, and do not use WebFetch: `curl -fsSL --create-dirs -o .claude/skills/update-wiki/SKILL.md https://raw.githubusercontent.com/davron-design/wiki-generator/main/templates/update-wiki.SKILL.md` Then tell me to start a new Claude Code session here and say `update`.

After that one paste, the skill keeps itself current along with everything else.

My wiki was set up with the old global option

Earlier versions could install the skills once for every project, in your home folder's ~/.claude/skills/. Claude Code runs those copies ahead of each wiki's own, so updates inside a wiki never reached them.

Say update inside the wiki, then say it once more after it finishes. The second run offers to move the global copies into a backup folder. If it reports "up to date" while the global copies are still there, do it by hand:

  1. In every other wiki without its own .claude/skills/ folder, say update, twice if needed, until that wiki has its own copies.
  2. Inside ~/.claude/, create a backup folder, for example wiki-skills-backup plus today's date, and move raw-compile, audit-wiki, update-wiki and .wiki-version from ~/.claude/skills/ into it. Renaming them inside skills/ leaves them active.
  3. In any wiki still without its own copies, paste the prompt above, start a new session there, and say update.
🎉
You now have a working wiki. Drop more files into raw/ whenever you have it, run compile to pull it in, and audit when you want a sanity check on what you've built.

02
Claude Code CLI

Level up with the CLI.

Everything so far runs in the desktop app — buttons, chat box, no terminal. The CLI is the same Claude Code in a terminal window, where it can also run commands and install tools for you. It's an optional power-up, not a requirement.

You don't need this. The desktop app from Section 01 already does everything in this guide. Reach for the CLI when you want Claude to run commands, install tools, and work faster — right inside your project folder.

What's a CLI?

CLI stands for command-line interface. Instead of clicking buttons, you type a short line into a black window called a terminal, press Enter, and the program responds — right there in text. That's the whole idea: you type, it does the thing.

Claude Code has a CLI version. You open a terminal, type claude, and you're chatting with the same assistant you already know — just in text, and with a few extra powers.

The Claude Code CLI in a terminal — the orange Claude mascot and version at the top, and an input box where you type. Describe what you want in plain English and press Enter, just like the desktop app.

Why use the CLI?

The desktop app is the friendly front door — great for reading, chatting, and everything in this guide. The CLI opens one extra door: because it runs in a real terminal, Claude can pick up its Bash tool and actually do things on your computer — run shell commands, install missing programs, and edit files directly.

That's exactly why installing a tool like Git is easier here: instead of downloading an installer by hand the way you did in Section 01, you can just tell the CLI "install git for me" and Claude runs it for you.

Everything in this beginner's guideEither — both are Claude Code

Same assistant, same account, same wiki folder. The CLI just lets Claude roll up its sleeves.

1

Install the Claude Code CLI

Pick your computer below, then paste the one line into your terminal and press Enter. It downloads and sets up the CLI for you — no other software to install first.

Open the Terminal app (press Cmd + Space and type Terminal), paste this, press Enter:

curl -fsSL https://claude.ai/install.sh | bash

Open PowerShell (press Start and type PowerShell), paste this, press Enter:

irm https://claude.ai/install.ps1 | iex

When it finishes, check it worked by typing:

claude --version

If you see a version number, you're set.

> claude 'claude' is not recognized

Seeing this? Totally normal, nothing's broken. Close your terminal window, open a fresh one, and type claude again — that's it. Works the same on Mac, Windows, or Linux.

2

Start Claude Code

Point your terminal at your wiki folder, then launch Claude Code:

claude

The first time you run it, Claude opens your browser to log in. Sign in with the same Claude account you already signed in with in Section 01 — nothing new to set up.

Once you're logged in, you're back at the > prompt, working in the exact same wiki folder — just type what you want in plain English, the same way you do in the desktop app.

⚡
Now Claude can install tools and run commands for you. Try asking it install git for me — in the CLI, it'll just do it.
03
Viewing in Obsidian

Browse your wiki visually.

Claude builds the wiki. Obsidian — a free markdown app — gives you a clickable, searchable, visual way to read it. Same folder. No sync needed.

What's Obsidian, and why use it?

Claude Code is great for building the wiki — compiling raw files, writing articles, running audits. But it's not designed for browsing what you've built.

Obsidian fills that gap. It's a free markdown reader that natively understands [[wiki links]] — the same link style Claude already writes into every article. That means:

  • Click any [[link]] in an article and jump to it.
  • Search across the whole wiki instantly.
  • See a graph view showing how topics connect.
  • Read your wiki on your phone or tablet too (optional).

Obsidian doesn't change your files. It just reads the same folder Claude is writing to.

1

Download Obsidian

  1. Go to obsidian.md.
  2. Click the big Get Obsidian button.
  3. Pick the installer for your computer (Mac, Windows, or Linux) and install it like any other app.

Obsidian is free for personal use — no account or sign-up required.

2

Open your wiki folder as a vault

In Obsidian, a "vault" is just a folder full of markdown files. Your wiki folder is already exactly that.

  1. Launch Obsidian.
  2. On the welcome screen, click Open folder as vault.
  3. Pick the wiki folder you created earlier (the one Claude Code is working in).
  4. Click Open.

Obsidian scans the folder and shows every markdown file in the left sidebar.

Tip: You can point Obsidian at the whole project folder (so you also see CLAUDE.md, raw/, etc.), or just the wiki/ subfolder if you only want to browse the polished knowledge base. Either works — pick whichever feels less cluttered.
3

Start at the master index

Your wiki has a built-in entry point.

  1. In the left sidebar, open wiki/_master-index.md.
  2. You'll see a table of every topic in your wiki.
  3. Click any [[link]] in the table to jump to that topic's index.
  4. From there, click into any article.

This is the same path Claude follows when answering questions — now you can walk it yourself.

4

Try the Graph View

This is the fun part.

Every article is a node. Every [[link]] between articles becomes an edge. Drag any dot to pull the graph around.

  1. Click the graph icon in the left sidebar (it looks like three connected dots), or press Ctrl/Cmd + G.
  2. You'll see every article in your wiki as a node, with lines connecting articles that link to each other.
  3. Click any node to jump straight to that article.

The graph is a quick way to spot orphaned articles (nothing links to them) and clusters (topics that are tightly connected). It's also a nice visual gut-check on how your wiki is growing.

5

Use search

Press Ctrl/Cmd + Shift + F to open the search panel. Type anything — Obsidian searches across every article instantly.

For quick file-name lookups, press Ctrl/Cmd + O and start typing an article name.

How Obsidian and Claude Code Work Together

You don't have to pick one. They share the same folder.

TaskUse
Drop new files into raw/Either (Obsidian or Finder)
Compile / audit / ask the wiki questionsClaude Code
Browse, search, follow links, read articlesObsidian
Edit an article by handEither

A common rhythm:

  1. In Claude Code, say compile to bring new files into the wiki.
  2. Switch to Obsidian to read what Claude wrote, follow the links, and check the graph.
  3. Spot something thin or missing? Back to Claude Code and say audit.
04
Work Together

Collaborate with your team.

Want a small team to build the same wiki together? Use GitHub Desktop as the syncing layer. No terminal, no coding.

What You'll Need (per person)
  • The Claude Code desktop app — you already have this
  • The GitHub Desktop app — desktop.github.com
  • A free GitHub account — github.com/signup
  • Git installed — you set this up back in Section 01, Step 1
ONCE
Team Lead

Set up the shared repo

  1. In GitHub Desktop, choose File → Add Local Repository and pick the wiki folder you created in Section 01. Since it isn't a Git repo yet, you'll see "This directory does not appear to be a Git repository" — click the create a repository link in that message.
  2. A Create a New Repository dialog opens with the Name and Local Path already filled in from your folder name (a folder named Work Knowledge Base becomes work-knowledge-base). Leave the defaults as they are and click Create Repository — this turns your folder into a local Git repo.
  3. Now click Publish repository (sign in to your GitHub account if prompted). In that dialog, keep Keep this code private checked if your files are sensitive, then publish. This creates the GitHub repo straight from your existing folder — no empty repo to reconcile.
  4. In the repo's Settings → Collaborators on github.com, invite your team members by username or email.
Team Member

Get a synced copy

  1. Install GitHub Desktop from desktop.github.com and sign in.
  2. Accept the email invitation from the team lead.
  3. In GitHub Desktop, click Clone a repository → pick your team's wiki → choose where to save it.

You now have a synced copy of the wiki on your machine.

DAILY
Everyone

Pull → Work → Push

The daily rhythm, named for the GitHub Desktop buttons you'll click.

01
Pull
Before you start
02
Work
As you go
03
Push
When you're done

01 — Pull. Open GitHub Desktop → Fetch origin → Pull origin to grab the latest changes from the team.

02 — Work. Open the wiki folder in Claude Code and work as usual — drop files into raw/, say compile, ask the wiki questions.

03 — Push. Back in GitHub Desktop, you'll see your changed files on the left. Type a short summary at the bottom (e.g. "Added onboarding notes"), then click Commit to main → Push origin.

Your team members can now Fetch → Pull to receive your changes.

Tips

Habits that prevent conflicts

  • Pull before you start. Push when you finish. That habit prevents most conflicts.
  • If two people edited the same article at the same time, GitHub Desktop will guide you through merging.
  • Everything is version-controlled — you can roll back any change from GitHub Desktop's History tab.
05
Advanced Collaboration

Pull Requests for bigger teams.

The "everyone pushes to main" flow above works for small, trusted teams. As your group grows — or when changes need a second pair of eyes before going live — switch to Pull Requests.

You don't need this if your team is small and trusts each other. Section 04's Pull → Work → Push loop is enough on its own. Come back here when your group grows, or when you want a second pair of eyes on every change before it goes live.

What's a Pull Request?

Think of a Pull Request (PR) as a draft change proposal. Instead of pushing your edits straight into the shared wiki, you save them on a personal "side track" (a branch) and ask a teammate to review them. Once approved, the change is merged into the main wiki — and everyone else pulls it down as normal.

It's the digital equivalent of "let me show you this before I publish it."

The wiki lives on main. To propose changes safely, you fork a side branch, work on it, open a PR, get reviewed, then merge back.

Two roles — Maintainers and Contributors

PRs introduce a split between two roles:

RoleWhoWhat they do
MaintainerTeam lead (1–2 people)Reviews PRs, approves or requests changes, merges into main, manages access
ContributorEveryone elseEdits the wiki on their own branch, opens a PR, responds to review feedback

The maintainer is not the only one who can edit the wiki — contributors do all the writing. The maintainer's job is to be the gatekeeper of main, making sure nothing inconsistent or accidental lands in the shared copy.

Maintainer

Once

Turn on branch protection

To require PRs (instead of letting anyone push directly to main):

  1. Go to your repo on github.com.
  2. Click Settings → Branches.
  3. Under Branch protection rules, click Add rule.
  4. Branch name pattern: main
  5. Check Require a pull request before merging.
  6. Click Create.

From now on, every change — even the maintainer's own — flows through a PR.

Daily

Reviewing a PR
  1. Open the PR on github.com (you'll get an email notification).
  2. Read the description and click the Files changed tab to see exactly what changed.
  3. Leave comments on specific lines if needed, or approve the PR.
  4. When ready, click Merge pull request → Confirm merge.
  5. Click Delete branch (the button appears after merge) — keeps the repo tidy.
Contributor

Daily

The PR workflow

1. Start a branch before editing. In GitHub Desktop, click the Current Branch dropdown → New Branch → name it after your change (e.g. add-onboarding-notes) → Create branch.

2. Edit as usual. Open the folder in Claude Code, drop files into raw/, say compile. Your changes are isolated to your branch — main is untouched.

3. Commit and push your branch. Write a commit message → Commit to <your-branch> → Publish branch (first time) or Push origin (after that).

4. Open the Pull Request. GitHub Desktop shows a Create Pull Request banner — click it. A browser tab opens on github.com. Add a short description of what changed and why → Create pull request.

5. Wait for review. Your maintainer gets notified. They'll either:

  • Approve and merge — your change goes live, and everyone else can pull it.
  • Request changes — they leave comments; you edit on the same branch, commit, and push. The PR updates automatically.
Tips

Keep PRs healthy

  • Keep branches short-lived. Open a PR, get it merged, delete the branch. Long-running branches drift from main and become painful to merge.
  • One PR per topic. Don't bundle "added onboarding notes + fixed typos + restructured wiki" into one PR — split them. Smaller PRs review faster and are easier to revert.
  • Write clear PR descriptions. A one-line title plus 2–3 sentences explaining what and why makes review much faster.
06
Multi-Level Wikis

A wiki of wikis.

When a program runs several workstreams in parallel — each with its own wiki — the cross-cutting picture gets lost. A master wiki is an AI-maintained synthesis layer that sits above two or more workstream wikis and surfaces what they share: decisions, dependencies, risks, and the places they quietly disagree.

View on GitHub
You only need this if you're running two or more wikis. A single team is well served by the wiki-generator from Section 01. Reach for the master pattern when separate workstreams each keep their own knowledge base, and someone needs the view across all of them.

What a master wiki does

The master never duplicates a workstream's content. Its only job is to answer the questions no single workstream can see:

  • Shared decisions — choices made in one workstream that quietly bind the others.
  • Cross-team dependencies — who is waiting on whom, and for what.
  • Risks that span teams — exposure no single wiki holds in full.
  • Timeline interlocks — milestones that have to line up across workstreams.
  • Conflicting approaches — two teams solving the same problem two different ways.

Every claim it makes links straight back to the source article in the workstream wiki it came from, so the synthesis stays auditable. The master-wiki-generator skill packages this whole flow. It sets up the master and, by default, a ready-to-use wiki for each workstream inside it. You install it the same way Section 01 installs /wiki-generator.

Each workstream wiki runs its own raw/ → wiki/ → output/ pipeline and sits in master-wiki/raw/, created there by the generator or synced in from its own repository. master-compile reads each workstream's wiki/ plus the cross-workstream files, and writes the synthesis into master-wiki/wiki/, one article per theme.

How the levels fit

The master has the same raw/, wiki/, output/ layout as any wiki and answers the same commands (compile, audit, update), through its own master skills. What differs is what lands in raw/:

What goes in raw/Where it livesLifecycle
Cross-workstream filesA loose file in the master's raw/Archived after each compile, like any source
A whole workstream wikiraw/<ws-slug>-wiki/Stays live and is never archived: created there by the generator, or a synced copy of a wiki kept in its own repository

The distinction matters. Loose files are one-time source material. Workstream folders are living inputs that change each time a team compiles its own wiki. Program-wide decisions, steering notes, and RFCs that touch multiple teams are the loose files; everything a single team owns stays in that team's wiki.

The compile flow

Two layers, two responsibilities:

WhoWhat they do
Workstream leadOpens their workstream's folder in its own Claude Code session and compiles as usual. A workstream wiki kept in its own repository gets synced into the master's raw/ afterwards
Master maintainerOpens the master folder and runs compile. The master reads each workstream's wiki/ and writes the synthesis

When the maintainer compiles, the master doesn't organize by workstream — it organizes by theme: Risks, Decisions, Dependencies, Timeline, and Open Questions. A reader should be able to open the master and understand the program, not navigate three separate wikis stitched together.

Tips

Keep the master honest

  • Link every claim back to source. The master is a synthesis, not a system of record. If a statement can't point to a workstream article, it doesn't belong.
  • Organize by theme, never by team. A section per workstream just recreates the silos you're trying to see past.
  • Cross-WS files stay loose; workstream wikis stay folders. Loose files get archived after compiling; the raw/<ws-slug>-wiki/ folders stay live, so re-syncing is a copy, not a merge.
  • Re-compile when a workstream ships. The synthesis is only as current as the last time you pulled the workstream wikis in.
  • Open the folder you're working on. A session opened at the master folder runs the master's skills, and one opened in a workstream's folder runs that workstream's. The master's settings file switches the workstream skills off at its root, so a stray compile there can't archive a workstream.

Keep the master current

Say update in a session opened at the master folder. It pulls the latest master templates, shows what changed, asks before writing anything, and lists the workstream wikis that are behind. Each of those updates with update in a session opened in its own folder, just like a standalone wiki.
